# NVIDIA enhancement completion requirements

Popcorn SR's completion goal includes all five primary NVIDIA video enhancements from [Visual Enhancer](https://github.com/Merserk/dlss5-visual-enhancer). This is an implementation and device-verification requirement. The published 0.2.0 preview does not meet it yet.

| Required stage | User controls to support | Current implementation gap |
|---|---|---|
| DLSS neural rendering | Style, intensity, passes, tone/structure, masks, temporal quality | No native Linux video renderer or verified compatible neural runtime |
| DLSS Super Resolution | DLAA, Quality, Balanced, Performance, Ultra Performance; preset and temporal quality | Native CUDA SDR video backend, controls and packaged Unraid → Spark → Unraid delivery verified in three codecs; representative quality and large/long jobs remain unverified |
| RTX Video Super Resolution | Quality 1–4, scale or custom dimensions | Current VFX API, four levels/strength/custom sizing, lossless pipeline gates and Astryx controls implemented; CPU contract/timing/delivery fixtures pass. Genuine VFX execution and compatible Spark runtime remain unverified |
| RTX Video HDR | Contrast, saturation, middle gray, peak luminance, precision | TrueHDR backend, lossless paired pipeline, capability gating and Astryx controls implemented; CPU diagnostics verify 10-bit transport/export/delivery. Genuine SDK execution, quality/metadata and physical paired acceptance remain unfinished |
| DLSS frame generation | Target FPS, engine mode, optical-flow quality | Native Vulkan SDR backend, target FPS/cascade controls and packaged Unraid → Spark → Unraid delivery passed in three codecs, including native SR/DLAA combinations and full-video continuation; representative quality and large/long jobs remain pending |

Stages must be independently selectable, with compatible combinations and ordering. A preview must exercise the same settings and backend as the full job. Each enabled stage must pass its own real processing check on the selected worker. Unsupported stages stay unavailable with an actionable reason; availability does not count as completion.

## Evidence required to close the goal

- Real SDK invocation and produced pixels for each NVIDIA stage. Conventional resize/interpolation/tone mapping cannot satisfy NVIDIA stage acceptance.
- Manager → worker → returned file tests for individual stages and supported combinations. Preserve the source checksum, audio, subtitles, attachments, chapters and timing.
- HDR results must contain actual 10-bit HDR pixels, correct color signaling and suitable metadata. A relabeled SDR stream fails acceptance.
- Generated frames must come from DLSSG, with the requested frame cadence and original duration. Reject a target at or below the incoming frame rate.
- Quality checks include moving detail, scene cuts, faces, text and light changes. A synthetic startup clip establishes execution, not representative library quality.
- Worker cancellation, restart, interrupted transfer, full/replaced scratch storage and clean shutdown must preserve originals and safely recover only owned temporary files.
- Linux NVIDIA workers must work both paired with a NAS and on the same host. The Unraid manager remains usable without a GPU. RTX 5080 device acceptance is deferred by the user; that does not waive implementation of any stage.

## Native Linux investigation

NVIDIA's [DLSS SDK](https://github.com/NVIDIA/DLSS/tree/374959484e79a640feaba44c93ac8cfb0a03f5b5/lib) contains Linux AMD64 and ARM64 libraries for Super Resolution, Ray Reconstruction and Frame Generation. The current inventory does not establish a native Linux neural-rendering runtime or complete RTX Video HDR backend.

On 2026-10-12, the physical DGX Spark initialized NGX through its ARM64 driver and successfully created a 128×96 → 256×192 DLSS Super Resolution feature using SDK 310.9.1. The CUDA capability query reported Super Resolution available, Video Super Resolution unavailable, and Frame Generation unsupported through that CUDA path. This does not rule out another supported API. A subsequent static-frame CUDA smoke check also passed DLSS evaluation and readback: all 196,608 output channel values were finite. The video acceptance that followed is described below; representative temporal image quality remains unverified.

The independently written [NGX diagnostic](../native/README.md) reports initialization and single-frame pixel verification separately from video readiness. Its test files, SDK copies and caches were created in RAM and removed. No SDK binary, proprietary reference implementation or extracted model weights are included in Popcorn SR's public source.

The subsequent independent native video bridge passed physical Spark processing of 48-frame, two-second generated SDR clips with H.264, HEVC and AV1 NVENC output. Each produced 384×256 from 192×128 input, with all frame timestamps matching exactly. A 38-frame variable-rate clip also retained exact timestamps. All 25 combinations of the five SR modes and Default/J/K/L/M preset hints passed three-frame SDK evaluation/readback checks; low/medium/high motion-estimation settings passed too. Native runtime shutdown/recreation was unstable, so each configuration uses a fresh subprocess. NVENC frame reordering is disabled in the timestamped AI pipe to avoid duplicated/shifted frame timestamps observed on this runtime. Test files, dependencies, SDK copies and caches were RAM-backed and removed; existing containers and images were preserved.

The dedicated ARM64 NGX Docker worker built from commit `3be022b7620c2c6fccbb88cb42768e93f82c94dd` also passed physical Spark acceptance. Its imported filesystem layers, environment and architecture matched the locally tested image. Startup verified all 25 mode/preset combinations. A Mac manager paired over a localhost SSH reverse tunnel and received five-second generated SDR previews in H.264/Performance/Default/high motion, HEVC/Quality/K/medium and AV1/DLAA/J/low, at 320×192, 240×144 and 160×96 respectively. Audio and transfer hashes were retained, originals were unchanged and job scratch was cleaned. The temporary worker image, container and RAM files were removed; before/after service and image inventories matched. No NAS resources were created.

This establishes native SDR execution, short-clip timing and dedicated packaged paired delivery. It does not establish representative library quality, faithful color reproduction, large-resolution/long-job behavior or NAS → native SR worker → NAS delivery. These remain acceptance gates. No other NVIDIA stage is implied by Super Resolution passing.

Separately provisioned NVIDIA components retain their [own terms](https://github.com/NVIDIA/DLSS/blob/main/LICENSE.txt). A proprietary reference application is a behavioral reference, not permission to copy or redistribute its implementation. Architecture/runtime constraints remain open completion requirements.

## Vulkan frame-generation progress

The independent headless Vulkan diagnostic subsequently passed on the same physical Spark. Vulkan identified GB10, all required extensions were available, and SDK Frame Generation requirements returned supported. NGX initialization, Frame Generation availability/initialization parameters, 256×192 RGBA8 feature creation and submitted initialization commands all succeeded. This corrects the API-specific CUDA limitation; it does not establish produced frames. The probe always reports `video_render_verified: false`, and no Frame Generation UI/worker engine is enabled by it.

The temporary test used an existing image with the host's matched Vulkan loader/graphics libraries. SDK files, executable, shader/driver caches and scratch were in owned RAM folders and removed with the container; existing service/image inventories matched. No new image or NAS resource was created. SDK wrapper signatures, architecture and graphics-library discovery must be preserved in future packaging. Subsequent pixel and video checks are described below; controls, preview/full delivery and combinations remain completion requirements.

The subsequent generated-frame pixel check also passed. Three 256×192 RGBA8 inputs used flat float depth and backward pixel motion. Each output image was seeded on the GPU before SDK evaluation; all 49,152 pixels were replaced on each frame. The reset frame copied its input with interpolation disabled. Both moving-frame evaluations reported interpolation enabled and output pixels different from both adjacent inputs. This proves genuine DLSSG-produced synthetic frames, with synchronization and CPU readback. The diagnostic still reports `video_render_verified: false`; the separate video adapter has its own evidence below. Temporary RAM resources and the existing-image container were removed; existing service/image inventories matched and the NAS remained untouched.

The independent Vulkan video bridge then passed physical Spark processing of a 48-frame, two-second SDR clip: H.264/high motion, HEVC/medium and AV1/low each produced 96 frames. Native 3×–6× produced 144/192/240/288 frames, and a 38-frame variable-rate clip produced 76 frames. Every result decoded fully. Timing error was at most 0.5 ms, and duration error at most 1 ms, within Matroska timestamp precision. The SDK reported a native maximum of five generated frames per pair (6× total). Cache/dependency/SDK/video files were in owned RAM storage and removed with the temporary existing-image container; service/image inventories matched. No NAS resource was created.

The low-level video bridge accepts 8-bit SDR, even dimensions and square pixels, and writes a video-only intermediate. The higher-level controller and worker now add target cadence, cascade modes and preserved-media delivery, as described below. Stage combinations and representative quality remain required. ## RTX Video runtime investigation — 2026-10-13

NVIDIA's September 2026 [VFX TrueHDR documentation](https://docs.nvidia.com/maxine/vfx/latest/Filters/TrueHDR.html) explicitly documents Linux execution with driver 570 or later. It specifies real RGBA8 SDR input and RGB10A2 output with BT.2020 primaries and PQ transfer, plus contrast, saturation, middle gray and peak-luminance controls. Linux HDR is therefore an available SDK path to investigate; it must not be dismissed solely because the reference application uses Windows.

The [current VFX collection](https://catalog.ngc.nvidia.com/orgs/nvidia/maxine/collections/maxine_vfx_sdk/-) lists x86-64 Linux/Windows and Windows on Arm, without establishing a Linux ARM64 package for Spark. The [Core resource](https://catalog.ngc.nvidia.com/orgs/nvidia/maxine/resources/vfx_sdk_core/-) requires NVIDIA Developer Program or enterprise access, and feature libraries/models are provisioned separately. Package availability, compatible architecture and genuine processing remain prerequisites; documentation is not Spark support evidence. No new VFX package was installed or proprietary runtime redistributed during this investigation.

The latest [VSR filter guide](https://docs.nvidia.com/maxine/vfx/latest/Filters/VideoSuperResolution.html) documents four genuine AI upscaling modes, distinct from its bicubic comparison mode. The Python VFX adapter now follows the current public NVIDIA sample API, with controls and actual render-check machinery. No compatible runtime has been executed here; CPU and UI fixtures do not close this gate. HDR implementation must also preserve real 10-bit pixels through encoding and validate color signaling; merely tagging 8-bit SDR output cannot close its gate. The available [VFX video-generation filter](https://docs.nvidia.com/maxine/vfx/latest/Filters/VideoFrameGeneration.html) does not establish the required DLSSG path or Linux ARM64 support and is not counted as a substitute for the verified native Vulkan backend.

NVIDIA's own [Vulkan renderer sample](https://github.com/nvpro-samples/vk_gltf_renderer/blob/main/src/dlss.hpp) includes a separate neural-rendering path and explicitly gates it on `USE_DLSSNR`, requiring a beta NGX SDK. This supplies a primary integration direction without proving that the public SR/FG bundle includes the matching neural feature or Linux ARM64 runtime. Native neural rendering still needs an authorized, compatible beta package and real video checks. Neither Ray Reconstruction nor a different image model can substitute for that requirement.

The official [NVIDIA Python wheel index](https://pypi.nvidia.com/nvidia-vfx/) was also inspected on 2026-10-13. Its latest listed VFX version, 0.2.0.0, provides Linux x86-64 and Windows AMD64/ARM64 wheels, but no Linux ARM64 wheel. This independently confirms a current Python packaging gap for Spark; it does not rule out a separately authorized native package. No wheel or SDK was installed on either device during this inventory check.
